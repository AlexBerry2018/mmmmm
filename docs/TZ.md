**Статус:** на согласовании — см. раздел 2 «Открытые вопросы»

## 1. Общие сведения

### 1.1 Назначение

Мультиагентная система (далее — МАС) — платформа, в которой несколько LLM-агентов
со специализированными ролями совместно решают сложную задачу пользователя:
разбивают её на подзадачи, выполняют их с помощью инструментов, проверяют
результаты друг друга и собирают итоговый ответ.

### 1.2 Цели

1. Решать задачи, которые не помещаются в один запрос к модели (многошаговые,
   требующие исследования, написания и проверки кода, работы с файлами/API).
2. Повысить качество результата за счёт разделения ролей (исполнитель ≠ проверяющий).
3. Обеспечить прозрачность: каждое действие агента журналируется и воспроизводимо.
4. Контролировать стоимость и безопасность: бюджеты, песочница, подтверждение
   человеком опасных действий.

### 1.3 Термины

| Термин | Определение |
|---|---|
| Агент | Процесс с ролью, системным промптом, набором инструментов и моделью LLM |
| Оркестратор | Агент-координатор: планирует, распределяет подзадачи, принимает результат |
| Задача (Task) | Единица работы с входом, ожидаемым результатом, статусом и бюджетом |
| Инструмент (Tool) | Функция, доступная агенту (поиск, файлы, код, HTTP, MCP-сервер) |
| Артефакт | Результат работы агента (текст, файл, код, отчёт), сохраняемый в хранилище |
| Сессия | Полный цикл обработки одного запроса пользователя |
| HITL | Human-in-the-loop — точка, где система ждёт решения человека |

## 3. Архитектура

### 3.1 Общая схема

```
             ┌──────────────┐
 Пользователь│  API / CLI   │
     ───────►│   Gateway    │
             └──────┬───────┘
                    │ сессия
             ┌──────▼───────┐        ┌───────────────┐
             │ Оркестратор  │◄──────►│  Хранилище    │
             │ (Planner)    │        │  состояния    │
             └──┬───┬───┬───┘        │  (Postgres)   │
      задачи    │   │   │            └───────────────┘
        ┌───────┘   │   └───────┐    ┌───────────────┐
  ┌─────▼────┐ ┌────▼─────┐ ┌───▼──────┐ │  Память      │
  │Researcher│ │  Coder   │ │ Reviewer │◄►│ (вектор. БД) │
  └─────┬────┘ └────┬─────┘ └───┬──────┘ └───────────────┘
        └───────────┼───────────┘
             ┌──────▼───────┐
             │  Tool Layer  │  поиск, файлы, песочница кода, HTTP, MCP
             └──────────────┘
```

### 3.2 Паттерн координации

Основной паттерн — **иерархический (orchestrator–workers)**:

1. Оркестратор получает запрос, при необходимости задаёт уточняющие вопросы.
2. Строит план — ориентированный ациклический граф (DAG) подзадач.
3. Назначает подзадачи агентам; независимые подзадачи выполняются параллельно.
4. Результат каждой подзадачи проходит проверку Reviewer'ом (если задано в плане).
5. Оркестратор агрегирует результаты, при неудаче перепланирует.

Агенты **не общаются напрямую** — только через оркестратор и общее хранилище
артефактов. Это упрощает трассировку и контроль бюджета.

### 3.3 Роли агентов (MVP)

| Агент | Ответственность | Модель (по умолчанию) | Инструменты |
|---|---|---|---|
| Orchestrator | Уточнение запроса, план, распределение, сборка ответа, перепланирование | `claude-opus-5-5` | управление задачами, чтение артефактов |
| Researcher | Поиск и сбор информации, выжимки с источниками | `claude-sonnet-5-5` | веб-поиск, fetch, чтение файлов, память |
| Coder | Написание и запуск кода, работа с файлами | `claude-sonnet-5-5` | файловая система (в рабочей папке), песочница выполнения |
| Reviewer | Проверка результата по критериям приёмки, вердикт «принять / доработать» с замечаниями | `claude-sonnet-5-5` | чтение артефактов, запуск тестов |
| Writer | Финальное оформление ответа/отчёта | `claude-haiku-5-5` | чтение артефактов |

Новые роли добавляются **декларативно** (YAML-конфиг) без изменения кода ядра.

## 4. Функциональные требования

### 4.1 Управление сессиями
- **FR-01.** Создание сессии по запросу пользователя (текст + опциональные файлы).
- **FR-02.** Получение статуса сессии и потоковая выдача событий (SSE/WebSocket).
- **FR-03.** Отмена сессии с корректной остановкой всех агентов.
- **FR-04.** Возобновление сессии после сбоя/перезапуска с последней контрольной точки.

### 4.2 Планирование
- **FR-05.** Оркестратор формирует план в структурированном виде (JSON по схеме, раздел 5.2).
- **FR-06.** План показывается пользователю; в режиме `plan_approval=true` выполнение начинается только после одобрения.
- **FR-07.** Перепланирование при провале подзадачи (не более N раз, настраивается, по умолчанию 2).
- **FR-08.** Параллельное выполнение независимых подзадач (лимит параллелизма настраивается).

### 4.3 Агенты
- **FR-09.** Описание агента в конфиге: имя, роль, системный промпт, модель, список инструментов, лимиты.
- **FR-10.** Каждый агент работает в цикле «модель → вызов инструмента → результат» до завершения или исчерпания лимита шагов.
- **FR-11.** Агент возвращает результат в структурированном виде: статус, артефакты, краткое резюме, уверенность.
- **FR-12.** Reviewer возвращает вердикт `accept | revise | reject` и список замечаний; при `revise` подзадача возвращается исполнителю (не более M итераций).

### 4.4 Инструменты
- **FR-13.** Единый интерфейс инструмента: имя, описание, JSON-схема входа, обработчик.
- **FR-14.** Подключение внешних инструментов через MCP-серверы.
- **FR-15.** Выполнение кода только в изолированной песочнице (контейнер без доступа к хосту, лимиты CPU/RAM/времени, сеть по allow-list).
- **FR-16.** Инструменты помечаются уровнем риска (`read`, `write`, `external`); для `external` и деструктивных действий — подтверждение человеком (HITL).

### 4.5 Память и контекст
- **FR-17.** Краткосрочная память: история сессии и артефакты, доступные всем агентам сессии.
- **FR-18.** Долгосрочная память: сохранение полезных фактов/решений между сессиями с поиском по смыслу.
- **FR-19.** Агенту передаётся только релевантный контекст (выжимка плана + входы его подзадачи), а не вся история.

### 4.6 Наблюдаемость
- **FR-20.** Журнал всех событий: сообщения, вызовы инструментов, токены, стоимость, длительность.
- **FR-21.** Трассировка сессии в виде дерева (сессия → задача → шаг агента → вызов инструмента).
- **FR-22.** Отчёт по сессии: план, кто что сделал, итоговая стоимость.

## 5. Протокол взаимодействия

### 5.1 Жизненный цикл задачи

```
pending → assigned → running → review → done
                        │         │
                        ▼         ▼
                     failed ◄── revise (→ running)
                        │
                        ▼
                   replanned / cancelled
```

Также: `waiting_human` — из любого активного состояния при HITL-запросе.

### 5.2 Схема задачи (упрощённо)

```json
{
  "id": "task_01",
  "session_id": "sess_abc",
  "parent_id": null,
  "depends_on": ["task_00"],
  "agent": "coder",
  "goal": "Написать функцию парсинга CSV и тесты к ней",
  "inputs": {"artifacts": ["art_12"]},
  "acceptance_criteria": ["Все тесты проходят", "Обработка пустого файла"],
  "review_required": true,
  "budget": {"max_steps": 30, "max_tokens": 200000, "max_usd": 0.5},
  "status": "pending"
}
```

### 5.3 Результат агента

```json
{
  "task_id": "task_01",
  "status": "success | partial | failed",
  "summary": "Краткое описание сделанного",
  "artifacts": ["art_15", "art_16"],
  "confidence": 0.85,
  "issues": []
}
```

## 6. Нефункциональные требования

### 6.1 Надёжность
- **NFR-01.** Повтор вызовов LLM/инструментов при временных ошибках (экспоненциальная задержка с джиттером, до 4 попыток).
- **NFR-02.** Состояние задач сохраняется после каждого шага — сбой процесса не теряет прогресс.
- **NFR-03.** Тайм-ауты на шаг агента, задачу и сессию.

### 6.2 Стоимость и производительность
- **NFR-04.** Жёсткие бюджеты (токены, $, шаги) на задачу и сессию; при исчерпании — остановка с частичным результатом.
- **NFR-05.** Кэширование промптов (системные промпты и описания инструментов).
- **NFR-06.** Время до первого события в потоке ≤ 3 с.

### 6.3 Безопасность
- **NFR-07.** Секреты (API-ключи) — только из переменных окружения/хранилища секретов, никогда не попадают в промпт и логи.
- **NFR-08.** Контент из внешних источников (веб, файлы, ответы API) помечается как недоверенный; инструкции из него не исполняются без подтверждения (защита от prompt injection).
- **NFR-09.** Принцип минимальных привилегий: агент получает только инструменты своей роли.
- **NFR-10.** Аутентификация API по токену; изоляция данных разных пользователей.

### 6.4 Сопровождаемость
- **NFR-11.** Покрытие ядра (оркестрация, протокол, бюджеты) модульными тестами ≥ 80 %.
- **NFR-12.** LLM в тестах подменяется заглушкой — тесты детерминированы и не тратят токены.
- **NFR-13.** Набор eval-сценариев (≥ 20 эталонных задач) для оценки качества при смене промптов/моделей.

## 9. Этапы работ и критерии приёмки

### Этап 1 — MVP (ядро)
- Оркестратор + Researcher + Coder + Reviewer, последовательное выполнение.
- CLI-запуск, хранение состояния в SQLite/Postgres, журнал событий.
- Бюджеты на задачу и сессию.

**Приёмка:** на 10 эталонных задачах система строит план, выполняет его и
возвращает результат; ≥ 7 из 10 приняты экспертом; ни одна сессия не превышает бюджет.

### Этап 2 — Продуктивный контур
- REST API + SSE, параллельное выполнение DAG, возобновление после сбоя.
- Песочница выполнения кода, HITL-подтверждения, MCP-инструменты.
- Трассировка и отчёт по стоимости.

**Приёмка:** принудительный перезапуск во время сессии не теряет прогресс;
деструктивное действие без подтверждения невозможно; eval-набор из 20 задач ≥ 80 %.

### Этап 3 — Развитие
- Долгосрочная память, веб-интерфейс, декларативное добавление новых ролей.
- Специализированные агенты под предметную область (по ответу на Q1).

**Приёмка:** новая роль добавляется только конфигом; результаты eval не хуже этапа 2.

## 10. Риски

| Риск | Мера |
|---|---|
| Зацикливание агентов (бесконечные доработки) | Лимиты итераций и шагов, жёсткие бюджеты |
| Рост стоимости | Модели по ролям, кэширование промптов, учёт стоимости в реальном времени |
| Галлюцинации и ошибки | Обязательная проверка Reviewer'ом, ссылки на источники, тесты для кода |
| Prompt injection из внешних данных | Маркировка недоверенного контента, HITL для рискованных инструментов |
| Сложность отладки | Полная трассировка и детерминированные тесты с заглушкой LLM |
